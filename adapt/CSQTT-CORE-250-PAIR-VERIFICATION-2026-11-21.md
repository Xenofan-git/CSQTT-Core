# CSQTT Core — результат проверки исходной версии 2.5.0

Дата: 21 ноября 2026 года. **Это аудит и тестирование, не изменение рабочего кода.**

## Источники

Оригинальный CSQTT 2.5.0: amurcanov/csqtt, тег v2.5.0,
коммит fd936ef087c34cc46f26111dc2361f43b8b03c07.

В ARM64 клиентский unit-test harness непосредственно включены неизменённые
rust-client/protocol.rs и shared/wire_protocol.rs из указанного тега;
для зависимости anyhow использован исходник 1.0.104, отдельно
скомпилированный с Rust 1.97.1. Данные тестовые файлы находятся
в временном каталоге VPS, не в рабочем репозитории.

Серверные тесты выполнялись из **уже существовавшего ARM64 тестового
ELF производной Rust-сборки 2.5.0** (с изоляционными изменениями и
добавленными тестами). Не выдавать эту сборку за побайтово оригинальный ELF.

Все динамические тесты проведены в пользовательском режиме QEMU ARM64
без VK, TUN, SSH, изменения iptables, systemd или системной маршрутизации.

## Что НЕ подтверждено

1. Сквозное соединение **двух реально запущенных** процессов Rust
   client 2.5.0 ↔ Rust server 2.5.0 в ARM64 VM. Отдельного готового
   ARM64 client 2.5.0 executable в изолированном VPS не найдено.
   Проверен именно оригинальный модуль client protocol, не полноценный клиент.
2. Приём текущей Go/Linux и sing-box сборкой новой Rust server 2.5.0
   реализации. Текущий старый integrated workflow собирает legacy
   клиент+сервер 2.1.9/WIRE-4. Успех модульных тестов **не доказывает**
   совместимость старой пары с новой.
3. Реальный Deploy обновления/отката серверного ELF 2.5.0 в ARM64 VM,
   а также живой VK/TURN и фактический TCP/UDP трафик.

Идентификаторы WIRE-3/WIRE-4 показывают различие версий, но без
сквозного теста не доказывают ни полную совместимость, ни её отсутствие.

## Минимальный следующий шаг

Собрать **оригинальный ARM64 Rust client 2.5.0** в одноразовом
изолированном окружении с достаточным диском и памятью; затем проверить
парное реальное подключение к серверу 2.5.0 (авторизация, TUNCONF,
TCP/UDP, восстановление). После этого проверить штатный адаптированный
Deploy 2.5.0 и отказ/rollback в отдельной ARM64 VM. Не переписывать Go,
Deploy, sing-box или существующие маршруты ради этой проверки.

### Проверка реального клиента и сервера

- GitHub Actions: https://github.com/Xenofan-git/CSQTT-Core/actions/runs/44833443344
- **PASS**: оригинальный тест windows_client_reaches_wsl_server_through_a_real_turn_channel_and_dispatcher, 1 passed, 0 failed. Реальный протокольный стек клиента из оригинального Rust-кода работает в отдельном test runner процессе с независимо запущенным оригинальным 2.5.0 Rust-сервером через внутренний искусственный TURN; успешно выполнены DTLS-SRTP, GETCONF/TUNCONF, ICMP request/reply. Сервер выполнялся в отдельном Linux network namespace, без маршрута в Интернет. Это реальное сквозное прохождение пакета через сервер, но НЕ запуск полного самостоятельного client ELF через его обычный CLI.
- **FAIL**: следующий штатный тест getconf_timeout_recovers_without_terminating_the_tunnel на исходном лимите 10 секунд (тестовый timeout первой отказавшей сессии). Падение: the timeout session did not complete: Elapsed(()). Непрерывные повторы DTLS и fallback до получения ошибки GETCONF занимают больше 10 секунд; сервер в журнале подтверждал многократный GETCONF -> TUNCONF. Поэтому итог всего workflow помечен FAILURE несмотря на отдельный успешный сквозной тест.
- **PASS в отдельной диагностике восстановления**: https://github.com/Xenofan-git/CSQTT-Core/actions/runs/44834213912 — SUCCESS. Для проверки изменён только тайм-аут в одноразовой копии оригинального Rust *теста* (ожидание первой сессии 10 -> 40 секунд). Исходные Rust-клиент и сервер, а также алгоритм восстановления не изменялись. Первое потерянное DTLS-соединение корректно завершилось после ожидания отсутствующего GETCONF, затем независимая вторая сессия успешно получила TUNCONF; тест 1 passed/0 failed за **23,86 секунды**, TURN-релей и сетевой namespace очищены.
- Разница времени подтверждается оригинальными тайм-аутами: DTLS fallback ~8 секунд и последовательные тайм-ауты GETCONF 0,4 + 0,8 + 1,6 + 3,0 секунды, суммарно потенциально дольше исходного тестового предела 10 секунд. Исходный 10-секундный тест остался FAIL; диагностика с 40 сек SUCCESS. Это основание корректировать *отдельный тест*, а не переписывать работающий протокол.
- Независимая Москва ARM64 VM: оригинальный сервер v2.5.0 ранее запущен в отдельном netns, поднял csqtt1 10.66.67.1/24, слушал локальный UDP 46920, затем тестовый процесс завершён и namespace удалён; работающий csqtt-core.service оставлен неизменным.

Ограничения: не доказано, что существующий Go/Linux из legacy WIRE-4
совместим с новым сервером WIRE-3; не проверена установка/откат нового
2.5.0 ELF и не выполнен полноценный запуск самостоятельного клиентского
ELF с реальной авторизацией VK. Финальный релиз всё ещё требует
одной изолированной интеграционной приёмки Go/sing-box/Deploy, без
изменения production NanoPi до её успешного завершения.
