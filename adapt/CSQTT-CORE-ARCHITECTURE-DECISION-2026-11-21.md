# CSQTT Core — проверка архитектуры, 21 ноября 2026 года

**Статус:** аудит исходников и точек сборки; не изменение рабочих сервисов.
**Проверенный коммит:** 429d704ec7202cc65020e984f7a83fbe5b72e600.
**Цель:** собственный CSQTT Core на базе CSQTT 2.5.0; от стороннего Linux-проекта оставить только метод автоматического получения VK-токена. Сейчас это требование ещё не выполнено.

## Фактическая схема

    7-вкладочная панель HTML/JS
             │ HTTP API
             ▼
    Go/Linux контроллер (пока собирается из адаптированного внешнего дерева)
      ├─ AppCore: база профилей, настройки, логи, VK workflow
      ├─ Bridge / LinuxRunner: Connect/Disconnect, запуск дочернего Rust-клиента
      ├─ TUN / Direct / policy routing table 202 / SOCKS5 :12500
      │           │
      │           ▼
      │       Rust CSQTT CLIENT ←── VPN-протокол ──→ Rust CSQTT SERVER (remote)
      ├─ собственный SingBoxManager ──→ независимый процесс sing-box
      │                                  вход :19180, выход CSQTT :12500
      │                                  + DIRECT + сторонние SOCKS5
      └─ API Deploy → собственная проверка → совместимый Go-адаптер
                      → старый SSH/SCP исполнитель → отдельный Rust DeployManager

    Gateway/WireGuard из Gateway/ — отдельный эксперимент, не обязательный
    компонент основной семивкладочной архитектуры.

Здесь Go не переносит сам VK/TURN-трафик по CSQTT, но управляет клиентским
Rust-процессом, TUN, SOCKS5, хранением конфигурации и состоянием подключения.
Отдельный Rust-сервер не содержит замену этим клиентским функциям.
Sing-box маршрутизирует потоки, но не выполняет CSQTT/VK-авторизацию.
Поэтому **просто удалить Go сейчас нельзя**.

## Проверенные исходные связи

- adapt/headless_main.go: собственная HTTP-панель, NewApp, startup, Connect,
  Disconnect, сохранение профилей/настроек, VK, логи, управление sing-box.
- adapt/singbox_manager_linux.go и singbox_config_linux.go: отдельный процесс
  sing-box, независимая конфигурация и lifecycle.
- adapt/csqtt_core_socks5_linux.go: свой SOCKS5 listener и маркировка выхода,
  соединяющие sing-box с TUN/CSQTT.
- Адаптированные Desktop/Linux/app_linux.go и Desktop/Libs/bridge.go в
  закреплённом внешнем дереве: реальный запуск Rust client, Bridge, TUN,
  Connect/Disconnect и мониторинг дочернего процесса.
- Desktop/Libs/common.go: AppCore/профили/DB/настройки/статусы; VK-код вынесен
  и в другие Go-файлы, поэтому внешнее дерево нельзя удалить одним импортом.
- adapt/csqtt_core_deploy_bridge_linux.go: внешний DeployProtocol, DeployLog
  и DeployBusy пока вызываются только через совместимый адаптер.
- Основная сборка .github/workflows/build-original-linux-arm64.yml: компилирует
  Go Linux controller, отдельный Rust client, отдельный Rust server и
  Rust DeployManager. Бинарник client-linux-arm64 — именно дочерний клиент.
- Gateway/README.md и Gateway/main.go: независимая старая схема WireGuard;
  не смешивать с новой политикой sing-box.

## ВАЖНО: две несовведённые серверные линии

Основной интегрированный Linux workflow берёт Rust-клиент из закреплённой
ветки отдельного CSQTT client source и Rust-сервер на базе CSQTT v2.1.9.
В оба вносятся согласованные патчи протокола WIRE-4/recovery.

Другая сборка — .github/workflows/csqtt-core-verified-arm64-release.yml —
создаёт производный Rust-сервер CSQTT v2.5.0 отдельно. То, что оба варианта
компилируются, НЕ доказывает взаимную совместимость клиент ↔ сервер, VK/TURN,
TUNCONF, TCP/UDP или совместимость Deploy. В частности, проверенный
ARM64 ELF v2.5.0 ещё не является автоматически тем сервером, который
устанавливается интегрированным Go workflow.

**Перед удалением старого исполнения и переписыванием Deploy обязательно
выбрать каноническую клиент/сервер пару от CSQTT 2.5.0 и проверить wire,
авторизацию, восстановление, TUNCONF и SOCKS5 на изолированном ARM64 стенде.**

## Решения по компонентам

| Компонент | Решение | Почему |
| --- | --- | --- |
| Собственная семивкладочная HTML/JS панель | Оставить | Уже не зависит от Flutter |
| Собственные sing-box manager, правила, Rule Set | Оставить | Независимый второй движок |
| CSQTT Rust client | Оставить, выбрать совместимую версию | Реальный клиент VPN-протокола |
| CSQTT Rust server | Выбрать одну каноническую v2.5.0 линию | Разные пути сборки ещё не сведены |
| Linux TUN/Direct/SOCKS5 и policy table 202 | Сохранить поведение | Клиентский dataplane и изоляция маршрутов |
| Go контроллер | Роль оставить, реализацию сделать собственной | Нужен lifecycle, профильная DB, VK и запуск Rust-клиента |
| Внешние Go AppCore/Bridge/другие протоколы | Постепенно заменить минимальным собственным модулем | Большая внешняя библиотека целиком не нужна |
| Старый Rust DeployManager и Go SSH transport | Перенести ПОСЛЕ выбора версии сервера | Иначе двойная миграция формата ELF/unit/установки |
| Flutter/Dart/Wails в headless-сборке | Не возвращать | Панель уже самостоятельная |
| Экспериментальный Gateway/WireGuard | Не объединять с основным продуктом | Иные таблицы, интерфейсы и порты |
| Старые systemd/DB/protocol IDs | Пока оставить для обратной совместимости | Изменять только с планом миграции и отката |
| Автоматический VK-токен | Сохранить нужный метод, без лишних протоколов | Прямое требование продукта |

## Рекомендуемая конечная архитектура

1. **CSQTT Core Go supervisor** (собственный минимальный Go код):
   HTTP API + конфигурации/профили + VK-token method + управление дочерним
   Rust client + клиентские TUN/Direct/SOCKS5 + manager отдельного sing-box.
2. **CSQTT Rust client**: фактический клиент CSQTT протокола и VPN-трафик.
3. **sing-box**: отдельный процесс с независимыми настройками и правилами;
   outbound к CSQTT SOCKS5 или DIRECT/дополнительным SOCKS5.
4. **CSQTT Rust server v2.5.0**: одна совместимая, верифицированная
   клиент-серверная пара и проверенная процедура обновления/отката.
5. **Deploy по запросу**: отдельный исполнитель установки, не обязательная
   постоянно работающая сетевая служба на NanoPi.

Не рекомендую переписывать весь Go контроллер на Rust только ради языка:
это заставит заново проверять работающие TUN/SOCKS5 и сетевую изоляцию.
Важно **заменить стороннюю зависимость**, а не менять язык или всю архитектуру.

## Порядок работ, без повторения старых тестов

1. Выбрать и зафиксировать совместимую пару Rust client/server v2.5.0;
   проверить протокол и installer-контракт изолированно.
2. Составить список минимально используемых методов AppCore/Bridge,
   удалить лишние протоколы/GUI и заменить внешний Go модуль собственным.
   Сохранить прежний HTTP API, конфигурации и semantics CONNECT/DISCONNECT.
3. Проверять Go изменения unit/race и точечными тестами затронутых интерфейсов;
   повторить сетевую ARM64 VM только при изменениях TUN, SOCKS5, Direct,
   клиента или других сетевых контрактов.
4. Перенести Deploy транспорт после выбора канонического серверного пакета;
   обязательно проверить отказ, cleanup секретов, install/uninstall/rollback.
5. Убрать оставшееся внешнее исходное дерево из сборки, выполнить отдельный
   аудит лицензий/происхождения кода: в проверенном внешнем Go-файле
   присутствует SPDX PolyForm-Noncommercial-1.0.0, не стоит без проверки
   переносить такой исходник в распространяемый продукт.
6. После завершения миграции — одна финальная комплексная приёмка
   зафиксированного SHA на ARM64, затем отдельно аппаратная проверка.

## Чего аудит НЕ подтвердил

- Готовой полностью автономной Go-сборки без внешних Libs пока нет.
- Wire-совместимость двух серверных линий пока не доказана.
- Реальное обновление/принудительный откат нового Rust ELF и
  авторизованный live CRUD остаются незакрытыми по реестру тестов.
- Нельзя изменять default route, рабочий NanoPi, HydraRoute Core или Keenetic.

**Итог:** Go не удалять вслепую и не переписывать целиком. Сохранить минимальный
собственный Go supervisor, исключить ненужный сторонний код, выбрать одну
каноническую клиент/сервер пару CSQTT 2.5.0, затем переносить Deploy.
